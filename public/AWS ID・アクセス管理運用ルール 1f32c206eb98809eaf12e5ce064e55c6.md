# AWS ID・アクセス管理運用ルール

Created by: Wah Yuk

## 管理の目途

1. リソースの分離
    
    各環境間でリソースを分離することで、相互の干渉を防ぎ、システムの安定性を向上させます。
    
2. アクセス権限の管理
    
    環境ごとに独立したIAMポリシーを適用することで、アクセス権限を細かく管理し、セキュリティを強化します。
    
3. コスト管理
    
    各環境のコスト支出を追跡・最適化しやすくなり、予算管理が効率的に行えます。
    
4. セキュリティとコンプライアンスの確保
    
    環境ごとのセキュリティおよびコンプライアンス要件を満たすことで、全体のガバナンスを強化します。
    

## 管理の基本方針

- **最小権限の原則**（Principle of Least Privilege）を厳守
- **AWS Organizations による一元管理と SCP（Service Control Policy）の適用**
- **CloudTrail によるすべての操作の記録**

### **プリンシパル**

- アカウント
    - 一時的なアクセス権を付与するためのエンティティで、ユーザーやサービスが引き受けることができます。
- ユーザー
    - **ルートユーザー**：AWS アカウント作成時に生成される最上位の権限を持つユーザー
        - MFAの有効化、強力なパスワード設定、アクセスキーの削除またはロック、および緊急時のみの使用に限定する
    - **IAM ユーザー**：特定の個人やアプリケーションに対して作成されるユーザー。個別の認証情報（ユーザー名、パスワード、アクセスキー）を持ち、特定の権限を付与できます。
    - **フェデレーテッドユーザー**（SAML、OIDCなど）：組織の既存のIDプロバイダー（例：Active Directoryなど）で管理されているユーザーが、一時的な認証情報（IAMロールを引き受けることによって取得）を使用してAWSリソースにアクセスするユーザー
- ロール
    - 一時的なアクセス権を付与するためのエンティティで、ユーザーやサービスが引き受けることができます。
- サービス
    - AWS のサービス自体がリソースにアクセスする際のプリンシパル

## 1. 利用者分類とその定義

### 1-1. 人的ユーザー

### 内部ユーザー（社内の従業員など）

- **システム管理者**：フル管理権限（MFA 必須、必要に応じて一時的な権限昇格）
- **開発者**：開発環境に対するフルアクセス、本番環境は ReadOnly またはリクエスト制
- **運用担当者**：モニタリング・トラブルシュート用アクセス、CloudWatch や SSM 利用権限
- **請求・会計担当**：Billing Console のみにアクセス可能
- **ReadOnly ユーザー**：環境全体の読み取り専用アクセス

### 外部ユーザー（関連会社・外注など）

- **協力会社の開発者**：時間制限付き、IAM Role + STS による一時的なアクセス
- **外部監査人など**：必要最低限の監査権限、ReadOnly + CloudTrail ログへのアクセス

### 1-2. 機械ユーザー

### AWS リソース（Lambda、EC2、StepFunctions CodeBuild など）

- 各サービスに必要最低限の IAM Role を付与（最小権限の原則）
- マネージドポリシーの使用を優先します

### 外部システム・運用ツール（オンプレミスサーバー、Azure VM、CI/CD ツール、監視ツール など）

- Cross-account Role または Cognito 経由で制御
- 必要に応じて IP 制限やセッション期間の制限を設定

## 2. 認証・認可方式の選定

| ユーザータイプ | 認証サービス | 備考 |
| --- | --- | --- |
| 内部ユーザー | IAM User + MFA | 特権ユーザーや敏感なデータを取り扱うユーザーに対してMFAを義務付ける |
| プログラムによるアクセス | IAM User + Access Key | 最小限の使用、定期的なローテーション必須 |
| 社内関連者とカスタマー | IAM, AWS SSO | AD 連携や SAML/Federation 対応 |
| 外部ユーザー | IAM Role + STS（AssumeRole） | 利用時間を制限 |
| Web アプリユーザー | Cognito | ユーザー ID 管理、Federated Login 対応 |
| モバイルアプリユーザー | Cognito | SNS 認証（Google, Apple, Facebook など）対応 |
| サーバ間通信 | IAM Role | Lambda, EC2 など |

## 3. ポリシー設計原則

- Inline Policy の使用は禁止（トラッキング不可、再利用性低）
- AWS 提供のマネージドポリシーは開発用に限る
- Resource/Condition レベルまで制限する（S3 の prefix 単位、IP 制限、Tag ベース制御など）
- ポリシーは必ず Git で管理、Terraform または CloudFormation で IaC 化

## 4. ユーザーライフサイクルに関する運用ルー

### 4.1 ユーザー作成フロー

- IAM ユーザーを新規作成する際の一般的な手順です
    
    ```mermaid
    flowchart TB
      Start([開始: ユーザー作成申請の提出])
      Approval[承認プロセス<br>（上長・インフラチーム）]
      UserType{ユーザーの種別判定}
      IAMUser[IAMユーザーの作成<br>（特定のユースケース）]
      SSOUser[社内ユーザー：<br>AWS IAM Identity Center連携]
      TempUser[一時的ユーザー：<br>STS + IAMロールの発行]
      ExternalUser[外部ユーザー：<br>Amazon Cognito経由で登録]
      Credentials[認証情報の発行<br>（パスワード/アクセスキー）]
      RoleAssignment[グループ登録・ロール割り当て]
      MFASetup[MFAの設定]
      Notification[ユーザーへの通知<br>（初期パスワード変更依頼）]
      Audit[CloudTrailによるアクセス監査]
      End([終了])
    
      Start --> Approval
      Approval --> UserType
      UserType --> IAMUser
      UserType --> SSOUser
      UserType --> TempUser
      UserType --> ExternalUser
    
      IAMUser --> Credentials
      SSOUser --> RoleAssignment
      TempUser --> RoleAssignment
      ExternalUser --> RoleAssignment
    
      Credentials --> RoleAssignment
      RoleAssignment --> MFASetup
      MFASetup --> Notification
      Notification --> Audit
      Audit --> End
    ```
    

### 4.2 権限変更フロー

- 既存ユーザーの権限変更申請から適用までの流れです。承認後に IAM コンソールでグループやロールを更新し、変更後は AWS Access Analyzer 等で最小権限を維持しているか確認します。
    
    ```mermaid
    
    flowchart TB
      P1[権限変更申請] --> P2[マネージャ承認]
      P2 --> P3[IAM でユーザー・グループ権限更新]
      P3 --> P4[AWS Access Analyzer で検証]
      P4 --> P5[完了通知]
    
    ```
    

### 4.3 ユーザー削除フロー

- 退職・異動などで不要になった場合のユーザー削除プロセスです。IAM 上のログインプロファイルを無効化し、利用キーを停止・削除します。不要リソースの移管後、最終的にユーザーを削除します。削除対象は CloudTrail 最終アクセスログ等で確認し、不要なユーザー・権限は速やかに削除します。
    
    ```mermaid
    
    flowchart TB
      D1[退職・異動通知] --> D2[IAM 認証情報無効化]
      D2 --> D3[EC2/EBS などリソース移管]
      D3 --> D4[IAM ユーザー削除]
      D4 --> D5[監査ログ更新]
    
    ```
    

## 6. 定期監査とセキュリティ強化策

- IAM Access Analyzer、Access Advisor で使用状況確認
- 定期的なポリシー見直しと不要権限の削除
- GuardDuty、Security Hub と連携して異常検知
- IAM Credential Report を用いてキーの使用状況を可視化

## 7. モバイル端末とプログラムによるアクセス

### 7-1. モバイル端末（スマートフォン等）

- Cognito を使用して、SNS 認証（Google, Apple, Facebook など）を統合
- モバイルアプリからのアクセスには、Cognito Identity Pool を活用して一時的な認証情報を発行

### 7-2. プログラムによるアクセス（API、CLI、SDK）

- IAM User によるアクセスキーの発行は最小限に留め、定期的なローテーションを実施
- 可能な限り、IAM Role を使用して一時的な認証情報を利用（例：EC2 Instance Profile、Lambda Execution Role）
- アクセスキーの使用状況は CloudTrail で監視し、不正使用を検知AWS Web Services

## 8. ゼロトラストセキュリティモデルの導入

- 「常に検証、決して信頼しない」の原則に基づき、すべてのアクセスリクエストを検証
- ユーザーとデバイスの認証を強化し、コンテキストに基づいたアクセス制御を実施
- 最小権限の原則を徹底し、必要最小限のアクセス権を付与
- ネットワーク境界に依存せず、リソース単位でのアクセス制御を実現

## 9. パスワードポリシー

- IAM ユーザーのパスワードは十分な強度を要求します。
- **最小文字数**は8文字以上、**大文字・小文字・数字・記号**を各1文字以上含む複雑性を設定します。
- パスワードにはアカウント名やメールアドレスを含めず、既知の単語の連続も避けます。
- **初期パスワード**は管理者が一時的に発行し、ログイン時に強制変更させます。
- パスワードの**有効期限**は365日程度（AWS上限は最大1095日）とし、期限切れ15〜14日前からコンソール上で警告を出して更新を促します。
- 過去に使用したパスワードの再利用禁止（直近5世代程度）や管理者リセットの必要有無設定も行います。

| 項目 | 設定値 |
| --- | --- |
| **最小文字数** | 8文字以上 |
| **文字種** | 大文字、小文字、数字、記号の組み合わせ |
| **パスワードの有効期間** | 365日 |
| **パスワードの再利用禁止** | 過去5回分のパスワード再利用禁止 |
| **初回ログイン時のパスワード変更強制** | 必須 |

## 10. AccessKey（アクセスキー）の運用ルール

- 開発者向けには、なるべく IAM ロール／一時認証情報（STS）を利用し、AccessKey の発行は最小限に留めます。
- キーをコードに埋め込まず、定期的に確認して不要なキーは無効化／削除します。また、アクセスキーに対してもアクセス許可境界（パーミッションバウンダリ）を設定し、付与できる権限の上限を制限する運用を検討します。
- **取得:** 開発人員からの申請に基づき、IAM管理者がIAMユーザーを作成し、Access Keyを発行します。
- **キーのローテーション**：発行から90日以内にローテーションを完了
- **未使用キーの削除**：90日以上使われていないキーは無効化・削除
- **STS/ロール活用**：なるべくアクセスキーを使わず、IAM ロール（STSセッション）でアクセス

| 項目 |  | 詳細説明 | 関連AWSサービス |
| --- | --- | --- | --- |
| **発行** | 最小権限で発行 | IAMグループを通じて必要最小限の権限を付与し、個別のIAMユーザーに発行する。 | IAM |
| **保管** | 安全な場所での保管 | 個人PCの安全な領域に保存し、バージョン管理システムや公開リポジトリへの誤コミットを厳禁とする。 | AWS Secrets Manager (検討) |
| **ローテーション** | 定期的な更新を義務化 | 90日ごとなど定期的にAccess Keyを削除し、新しいキーを発行する。 | IAM |
| **MFA適用** | プログラムアクセスにもMFAを強制 | MFAで認証されていないリクエストを拒否するIAMポリシーを適用し、Access Key漏洩時の不正利用を防ぐ。 | IAM, MFAデバイス |
| **監査** | 利用状況の監視 | AWS CloudTrailを用いてAccess Keyの利用履歴を監視し、異常なアクティビティを検出する。 | AWS CloudTrail |

## マルチアカウント管理

### 1. AWS Organizations によるアカウント統合管理

- AWS Organizations を使用して、複数の AWS アカウントを一元的に管理します。
- 組織単位（OU）を活用し、職能（例：セキュリティ、インフラ）や**ライフサイクル（例：開発、ステージング、本番）**に応じてアカウントを分類します。
- OU ごとにポリシーを適用することで、柔軟なアクセス制御が可能となります。

### 2. 管理アカウントのセキュリティ強化

- 管理アカウントへのアクセスは、最小限の信頼された管理者に限定します。
- ルートユーザーの認証情報（メールアドレス、パスワード、MFA）の管理を厳格に行い、定期的な確認と更新を実施します。
- 管理アカウントにはワークロードをデプロイせず、組織の管理タスク専用とします。

### 3. サービスコントロールポリシー（SCP）の活用

- SCP を使用して、組織内のアカウントや OU に対して最大許可権限を定義します。
- SCP は IAM ポリシーと組み合わせて使用され、明示的に拒否された操作は実行できません。
- 例として、特定のリージョンやサービスの使用を制限する SCP を設定できます。

### 4. クロスアカウントアクセスの管理

- IAM ロールの信頼ポリシーを設定し、他のアカウントからのロール引き受けを許可します。
- 例として、セキュリティアカウントに「組織管理者ロール」を作成し、他のアカウントの管理者が SAML や CLI を通じてこのロールを引き受けることで、統一的な管理を実現します。
- AWS Control Tower では、このようなロールの設定がデフォルトで行われます。
